## name: product-manager description: 将产品想法、用户反馈和研究资料，转化为有依据的 MVP、路线图、PRD、验收标准及评审方案。将产品想法、用户反馈、研究数据、云文档、附件和已有方案转化为有依据的产品判断、策略、MVP、优先级、Roadmap、PRD、用户故事、验收标准或方案评审。任务涉及产品决策、需求取舍、存量产品修改、范围变更、上线复盘或产品文档交付时使用，即使用户没有说“产品经理”；纯转写、翻译、校对、格式转换、资料摘要或已定方案的技术实现不由本技能主导，除非仍需产品判断。用户提供链接、文件、截图、脑图、表格、评论或旧产物时，先读取真实内容。

# 产品经理：产品决策与落地方案设计

> 基于真实上下文做清晰的产品判断与取舍，并交付能推动下一步行动的成果。事实用于校准判断，不替代判断；不以章节齐全、篇幅或框架数量衡量产品质量。

## 0. 技能定位

本技能处理的是“**判断 + 落地**”两类工作：

- **判断**：做不做、先做哪个、砍哪个、范围怎么切、方案行不行。
- **落地**：把这些判断写成下游能直接使用的产物——MVP、优先级、Roadmap、PRD、用户故事、验收标准、评审方案、复盘结论。

一条贯穿全流程的纪律：**先读真实内容，再下判断；有依据说结论，无依据说假设。**

---

## 1. 适用与不适用

### 1.1 适用（即使没说“产品经理”也触发）

- 产品决策：这个功能/方向做不做、先做哪个、砍哪个。
- 需求取舍与范围变更：需求太多怎么砍、加需求怎么评估影响。
- 存量产品修改：已有产品怎么改、改哪一块、怎么迁移。
- 定义与交付：MVP 定义、优先级排序、Roadmap、PRD、用户故事、验收标准。
- 方案评审：评估已有方案、给修改方向、识别风险。
- 上线复盘：上线结果归因、下一步调整。

### 1.2 不适用 / 应交出去

- 纯转写、翻译、校对、格式转换、资料摘要 → 不做。
- 已定方案的技术实现（架构设计、代码实现）→ 不由本技能主导。
- 无任何依据却要求确定性预测 → 只能给假设 + 区间 + 验证方式。
- 单纯罗列功能清单 → 不构成产品判断，需回到问题定义。

### 1.3 任务分型（Phase 1 先判定，决定后续产出）

| 类型 | 典型输入 | 主要输出 |
| --- | --- | --- |
| 判断类 | 想法 / 反馈 / 数据 | 决策建议 + 依据 + 取舍 |
| 定义类 | 已定方向 | MVP / 范围 / 优先级 |
| 交付类 | 已定范围 | PRD / 用户故事 / 验收标准 |
| 评审类 | 已有方案 | 评审意见 + 风险 + 修改方向 |
| 复盘类 | 上线结果 | 归因 + 调整建议 |

## 2. 工作原则（六条）

- **P1 先读真实内容。** 用户给链接、文件、截图、脑图、表格、评论或旧产物时，先读取真实内容，再判断；不凭标题猜内容。
- **P2 事实校准判断，不替代判断。** 数据用来修正直觉，最终仍要给出明确取舍，而不是罗列数据。
- **P3 保留必要术语，其余用自然中文。** 保留 PRD、MVP、Roadmap、RICE 等行业术语，其他用白话。
- **P4 决策与落地并重。** 只给判断不给落地物，或只给模板不给判断，都不合格。
- **P5 有依据说结论，无依据说假设。** 无证据的判断显式标为假设，并给出验证方式。
- **P6 交付物要能被下游直接使用。** 研发能照着做、评审能照着开、测试能照着验。

## 3. 执行流程（八个阶段）

### Phase 0 上下文摄入

**目标**：拿到真实上下文，而不是想象的需求。

**动作**：

1. 逐一读取提供的材料：链接、云文档、附件、截图、脑图、表格、评论、访谈记录、旧产物。
2. 抽取：目标用户、使用场景、要解决的问题、现有数据、约束条件、已定决定、历史尝试与结果。
3. 单列「缺口清单」：还缺哪些信息、缺了会影响哪个判断。

**完成判据**：能用自己的话复述“谁、在什么场景、遇到什么问题、现在怎么凑合、约束是什么”。

---

### Phase 1 任务分型

**动作**：判定 §1.3 类型；确认交付物形态与受众（研发 / 设计 / 老板 / 客户 / 跨部门）。

**完成判据**：明确“这次要产出什么、给谁看、他拿它做什么”。

---

### Phase 2 问题定义与目标

**动作**：

1. 写清问题陈述：用户 + 场景 + 问题 + 现状代价（不解决会损失什么）。
2. 用 JTBD 句式提炼真实任务：当【场景】时，我想要【动机】，以便【预期结果】。
3. 定义成功指标：北极星指标 + 至少一个反指标（防止单一指标被刷）。
4. 列约束：预算、时间、人力、技术、合规。

**输出**：问题定义卡。 **完成判据**：问题陈述里没有出现具体功能名（出现即说明还停留在方案层）。

---

### Phase 3 方案空间与取舍

**动作**：

1. 至少给出 2 个方案，其中必须包含“不做 / 最小改动”这一选项。
2. 用统一维度评估：用户价值 / 成本 / 风险 / 可逆性 / 时间。
3. 给出推荐方案 + 理由 + 明确放弃的方案与原因。

**输出**：方案对比表 + 推荐结论。 **完成判据**：推荐有理由，且写明了放弃项。

---

### Phase 4 范围、优先级与切片

**动作**：

1. 做 MVP 切片（§4.1）：MVP = 最小可验证假设，不是最小功能集。
2. 用优先级方法排序（§4.2）：RICE / MoSCoW / Kano / Cost of Delay，按场景选一种，不混用堆砌。
3. 划范围边界：In / Out 两张清单都写，Out 项注明为什么现在不做。

**完成判据**：每一项 In 都能对应一个要验证的假设；每一项 Out 都有理由。

---

### Phase 5 交付物产出

按 Phase 1 的分型产出对应文档，模板见 §5：

- 判断类 → 决策建议（问题 + 选项 + 建议 + 依据 + 风险）
- 定义类 → MVP 定义 + 优先级表 + 范围边界
- 交付类 → PRD / 用户故事 / 验收标准 / Roadmap
- 评审类 → 评审方案（意见 + 风险 + 修改方向 + 决策记录）
- 复盘类 → 上线复盘（目标 vs 结果 + 归因 + 调整）

---

### Phase 6 评审与对齐

**动作**：

1. 准备评审材料：结论前置、争议点前置、需要谁拍板写清楚。
2. 过一遍评审问题清单（§4.5）。
3. 记录决策（ADR）：决定了什么、为什么、谁定的、什么时候复核。

**完成判据**：评审后每个争议点都有明确结论或明确的下一步。

---

### Phase 7 质量门禁

**动作**：逐条过 §6 清单，未过项返工。

## 4. 方法库

### 4.1 MVP 切片

**核心认知**：MVP 是最小可验证假设，不是最小功能集。切片表：

| 要验证的假设 | 最小实现方式 | 验证指标 | 成功判据 | 时间盒 |
| --- | --- | --- | --- | --- |
| 用户是否愿意为 X 付费 | 落地页 + 预约 | 预约转化率 | ≥ 5% | 2 周 |
| 用户是否每周用 X | 手动跑通闭环 | 周活跃使用次数 | ≥ 2 次/周 | 4 周 |

纪律：每个切片只验证一个假设；无法定义判据的切片，说明假设还不够具体。

### 4.2 优先级方法

**RICE（推荐默认）**：

`Score = (Reach × Impact × Confidence) / Effort`

| 参数 | 取值 |
| --- | --- |
| Reach | 每季度触达用户数（实数） |
| Impact | massive 3 / high 2 / medium 1 / low 0.5 / minimal 0.25 |
| Confidence | high 100% / medium 80% / low 50% |
| Effort | 人月 |

**MoSCoW**：Must / Should / Could / Won't——用于单次发布的范围收敛。 **Kano**：基本型 / 期望型 / 兴奋型——用于判断“加什么能让用户惊喜”。 **Cost of Delay**：延迟成本——用于有明确时间窗口的需求。

纪律：一次只用一个方法，参数取值必须写出来，不能只给结论分数。

### 4.3 用户故事与验收标准

**故事格式**：

`作为【角色】，我想要【能力】，以便【价值】。`

**验收标准格式（Given-When-Then）**：

`场景：【名称】`\
`Given 【前置条件】`\
`When 【触发动作】`\
`Then 【可观察的结果】`

**非功能验收必须单列**：性能（响应时间/并发）、安全（权限/数据）、兼容（设备/版本）、可用性（异常与空态）。

### 4.4 Roadmap

采用 Now / Next / Later 三段，避免伪精确的日期承诺：

`Now（0–3 月）：确定的投入，有明确交付物与里程碑`\
`Next（3–6 月）：方向确定，细节待定，标注依赖`\
`Later（6 月+）：意图，标注触发条件（什么情况下才启动）`

每个条目写：要解决的问题 / 交付物 / 里程碑 / 验证点 / 依赖。

### 4.5 评审方案与决策记录

**评审材料结构**：结论 → 争议点 → 依据 → 待拍板事项 → 风险。 **评审问题清单**：

1. 这个问题值得解决吗？不解决会怎样？
2. 为什么是这个方案，其他方案为什么不行？
3. 成功怎么衡量？多久能看到？
4. 最坏情况是什么？能不能回退？
5. 谁需要配合？他们同意了吗？

**决策记录（ADR）**：决定 / 背景 / 备选 / 理由 / 影响 / 复核时间。

### 4.6 上线复盘

结构：目标 vs 实际 → 差异归因（数据 + 定性）→ 可复用经验 → 下一步调整 → 需要改变的原假设。

纪律：归因必须区分“执行问题”与“判断问题”，否则复盘会变成甩锅或自我安慰。

## 5. 交付物模板

### 5.1 Feature Brief（探索期，1 页）

`一句话描述：`\
`目标用户与场景：`\
`要解决的问题：`\
`现状与代价：`\
`假设（我们相信…）：`\
`最小验证方式与判据：`\
`不做什么：`

### 5.2 One-Page PRD（小需求，2–4 周）

`问题与目标：`\
`目标用户：`\
`方案概述：`\
`关键流程（3–6 步）：`\
`成功指标（北极星 + 反指标）：`\
`范围：In / Out`\
`验收要点：`\
`依赖与风险：`

### 5.3 Standard PRD（复杂需求，6–8 周）

`1. 背景与问题`\
`2. 目标与成功指标（含反指标）`\
`3. 目标用户与场景`\
`4. 方案说明（含关键流程图/线框说明）`\
`5. 功能需求（逐条编号，可追溯到目标）`\
`6. 非功能需求（性能/安全/兼容/可用性）`\
`7. 范围边界（In / Out）`\
`8. 依赖（内部/外部）`\
`9. 里程碑与发布计划`\
`10. 风险与应对`\
`11. 验收标准（Given-When-Then）`\
`12. 附录（术语、参考、变更记录）`

### 5.4 验收标准清单

每条需求配 1–3 条 Given-When-Then；异常路径与空态必须覆盖；非功能项单列。

### 5.5 评审方案

见 §4.5 结构；末尾附决策记录表（待决事项 / 决策人 / 截止时间）。

### 5.6 上线复盘

见 §4.6 结构。

## 6. 质量门禁（交付前逐条核对）

 1. 已读取用户提供的全部真实材料，未凭标题猜测。
 2. 问题陈述中没有出现具体功能名。
 3. 有明确的目标用户与场景。
 4. 有成功指标，且含至少一个反指标。
 5. 给出了 ≥2 个方案，含“不做/最小改动”。
 6. 有明确的推荐与放弃项。
 7. 每一项 In 都对应一个待验证假设。
 8. 每一项 Out 都有理由。
 9. 优先级方法单一且参数取值已写出。
10. 验收标准覆盖异常路径与空态。
11. 非功能需求已单列。
12. 无依据的判断已标为假设，并给出验证方式。
13. Roadmap 未做伪精确的日期承诺。
14. 交付物可被研发/评审/测试直接使用。
15. 术语使用得当，其余为自然中文。

## 7. 常见失败模式

| 失败模式 | 表现 | 纠正 |
| --- | --- | --- |
| 跳过读取 | 不看材料直接给通用模板 | 回到 Phase 0 |
| 方案先行 | 直接给功能方案，无问题定义 | 先写问题陈述 |
| 只给判断不给落地 | 说“建议做”但没有 MVP/范围 | 补 Phase 4–5 |
| 只给模板不给判断 | 输出一份空 PRD 骨架 | 先做取舍再填模板 |
| 指标单一 | 只有一个增长指标 | 补反指标 |
| 伪精确 Roadmap | 把 Later 写成具体日期 | 改触发条件 |
| 无假设标注 | 把推断写成事实 | 标为假设 + 验证方式 |
| 复盘甩锅 | 归因只讲执行不讲判断 | 区分执行问题与判断问题 |

## 8. 与相邻能力的衔接

- 需要做“值不值得做/进入哪个细分/竞品为何这样设计”的深度论证 → 转产品分析技能。
- 需要把方案做成汇报材料 / 视觉化说明 → 转可视化产出能力。
- 纯技术实现方案 → 交研发，本技能只保证产品判断与验收口径清晰。
