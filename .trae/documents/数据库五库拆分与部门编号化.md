# 数据库重构：五库拆分 + 部门编号化

## 一、Summary（目标）

把当前 3 个 SQLite 库重构成 **5 个库**，并新增 **部门表（departments）** 让所有含部门的表只存编号（`dept-01` 形态），显示时统一由服务端解析成部门名。

用户原话拆解：
1. 工单、知识库从 AI-Flows 库里分出去 → **知识库独立成库**（工单保持现有独立库，知识库再拆一个）。
2. 新建部门表，每个部门一个编号；员工/节点/工单/评审等所有部门字段只存编号，便于部门改名。
3. 原 `ai-flows.sqlite`（主库）改名为 `users.sqlite`（承载账号域）。
4. 节点设置、仓库管理、管线、配置分出去放到新的 `ai-flows.sqlite`（AI-Flows 域）。
5. 保留旧库自动迁移，现有数据不丢。

已确认决策：编号形态 **`dept-01`（TEXT）**；部门表 **自动收集 + 内置种子**；**全量统一**所有含部门字段的表都改存编号。

| 库文件 | schema | 表 |
|--------|--------|----|
| `db/ai-flows.sqlite`（main） | main | settings, users, repos, pipelines, nodes, chat_accounts, review_accounts, messages, **kb_articles**, token_usage |
| `db/ai-chat-reviews.sqlite` | chat_reviews | chat_sessions, chat_messages, chat_models, reviews |
| `db/ai-tickets.sqlite` | tickets | tickets, ticket_comments |

- 主库表 SQL **无 schema 前缀**；子库 SQL 带前缀（`chat_reviews.` / `tickets.`）。

### 部门字段的代码触点

- 服务端 `platform.ts` **全部按“部门名”使用**（权限比较 `user.department === node.department`、展示、建工单、部门下拉来源）——共 55 处。
- 前端 13 个文件 69 处，基本是展示；`web/ai-pipeline-app.js` L17-18 有一份硬编码部门列表 `DEPARTMENTS`。
- **关键结论**：只要在 `db.ts` 的读写边界把“编号↔名称”就地互转（读出行→名称、写入前→编号），`platform.ts` 与前端可**几乎不改**，风险大幅降低。

## 三、Target Architecture（五库）

| 库文件 | schema | 表 |
|--------|--------|----|
| `db/users.sqlite`（**新主库**，原 ai-flows 改名） | main | **departments（新）**, users, chat_accounts, review_accounts, messages, token_usage |
| `db/ai-flows.sqlite`（**新，AI-Flows 域**） | ai_flows | settings, repos, pipelines, nodes |
| `db/ai-tickets.sqlite` | tickets | tickets, ticket_comments |
| `db/ai-kb.sqlite`（**新**） | kb | kb_articles |
| `db/ai-chat-reviews.sqlite` | chat_reviews | chat_sessions, chat_messages, chat_models, reviews |

### 部门表 DDL（放 main）

```sql
CREATE TABLE IF NOT EXISTS departments (
  ord        INTEGER NOT NULL,
  id         TEXT PRIMARY KEY,      -- dept-01 / dept-02 …
  name       TEXT NOT NULL UNIQUE,  -- 用户研究部 / 程序中台 / 平台运营部 …
  created_at TEXT NOT NULL
);
```

编号规则：内置种子固定顺序 `用户研究部→dept-01`、`程序中台→dept-02`、`平台运营部→dept-03`；其余从存量数据收集到的部门名按名称排序，依次 `dept-04`、`dept-05`…（两位补零）。

**不加外键**：nodes/tickets/reviews/kb 分处不同库，SQLite 不支持跨 schema 外键；沿用现有“逻辑关联 + get-or-create”约定。

## 四、Proposed Changes

### 1. `src/sqlite.ts`（核心）

**常量**（替换现有 `DB_FILE` 等）：
- `USERS_DB_FILE = db/users.sqlite`（新主库）、`AI_FLOWS_DB_FILE = db/ai-flows.sqlite`、`TICKETS_DB_FILE`、`KB_DB_FILE = db/ai-kb.sqlite`、`CHAT_REVIEWS_DB_FILE`。
- schema 常量：`AI_FLOWS_SCHEMA="ai_flows"`、`TICKETS_SCHEMA="tickets"`、`KB_SCHEMA="kb"`、`CHAT_REVIEWS_SCHEMA="chat_reviews"`，main 不加前缀。
- 删除旧 `DB_FILE` 导出（仅 sqlite.ts 内部使用，外部无引用，已核实）。

**DDL 重组**：
- `MAIN_SCHEMA_SQL`（users.sqlite）：新增 `departments`；保留 users / chat_accounts / review_accounts / messages / token_usage；**移除** settings、repos、pipelines、nodes、kb_articles。
- 新增 `AI_FLOWS_SCHEMA_SQL`（ai_flows.settings/repos/pipelines/nodes，全部加 `ai_flows.` 前缀）。
- 新增 `KB_SCHEMA_SQL`（kb.kb_articles，加 `kb.` 前缀 + `idx_kb_updated`）。
- `TICKETS_SCHEMA_SQL` / `CHAT_REVIEWS_SCHEMA_SQL` 不变。

**`getDb()` 流程改造**：
1. 开主库 `USERS_DB_FILE`，开 WAL + 外键。
2. `ATTACH`：`ai-flows.sqlite→ai_flows`、`ai-tickets.sqlite→tickets`、`ai-kb.sqlite→kb`、`ai-chat-reviews.sqlite→chat_reviews`。
3. 执行四段 DDL（main / ai_flows / tickets / kb / chat_reviews）。
4. `ensureColumn` 全部改成对应新 schema（`users.password_changed_at` 留 main；`repos.owner_email`、`nodes.*`、`nodes.pipeline_id` 改 `ai_flows`；tickets / chat_messages 不变）；`idx_nodes_pipeline` 索引改 `ai_flows.nodes`。
5. `migrateLegacyLayout(c)`（新，替代/扩展 `migrateLegacyTables`）：
   - 若 `ai_flows` schema 里存在 `users` 表（= 老 `ai-flows.sqlite` 作为旧主库），把 main 域表整表搬到 main：`users`、`chat_accounts`、`review_accounts`、`messages`、`token_usage`；把 `kb_articles` 搬到 `kb`；把可能残留的 `chat_sessions/chat_messages/chat_models/reviews`→`chat_reviews`、`tickets/ticket_comments`→`tickets`；搬完从 `ai_flows` DROP。幂等（无 `users` 表即跳过）。
   - 保留对 main 内遗留子库表的搬运兜底。
6. `ensureDepartments(c)`（新）：
   - 保证三个内置种子存在（按固定顺序编号）。
   - 扫描 users/review_accounts/nodes/tickets/ticket_comments/reviews/kb_articles 里出现过的部门值（含 JSON 列解析），是**部门名**且不在表中则按序补 `dept-NN`。
7. `normalizeDepartmentColumns(c)`（新，幂等）：对每张含部门列的表，按 departments 逐行 `UPDATE <schema>.<table> SET department = :id WHERE department = :name`（**只按名称精确匹配**，已是编号的行不动，避免误置 NULL）；`kb_articles.departments` 与 `nodes.executors/removed_executors` 的 JSON 在 JS 里 parse→映射→序列化。

### 2. `src/db.ts`（数据访问层）

**schema 前缀修正**（机械替换，约 50 条 SQL）：
- `settings` / `repos` / `pipelines` / `nodes` → 加 `ai_flows.` 前缀（含 `importLegacyJson`、`ensureDefaultPipeline`、`createPipeline`、`deletePipeline`/`deleteRepo` 联动、各 `load*/save*/append*/update*`）。
- `kb_articles` → 加 `kb.` 前缀（`KB_INSERT_SQL`、`loadKbArticles`、`saveKbArticles`、`updateKbArticle`、`deleteKbArticle`）。
- `nextOrd(c, table)` 调用：表名改全限定（`ai_flows.nodes`、`kb.kb_articles`、`tickets.tickets` 等）。
- `users` / `chat_accounts` / `review_accounts` / `messages` / `token_usage` / `departments` 保持 main 无前缀。

**部门编号↔名称翻译（核心，`db.ts` 内新增私有 helper）**：
- `loadDepartmentIndex()`：读 `SELECT id,name FROM departments`，返回 `byId`/`byName` 两个 Map（进程内按需缓存，写 departments 时失效）。
- `departmentIdOf(name)`：get-or-create（不存在则 `dept-NN` 序号新增）→ 返回编号。
- `departmentNameOf(idOrName)`：命中编号→名称；否则原样返回（容忍历史脏值）。
- 替换点：
  - `userParams`：`department: departmentIdOf(u.department)`；`rowToUser`：`department: departmentNameOf(r.department)`。
  - `nodeParams`/`rowToNode`：`department` 同上；`executors`/`removed_executors` 的 `from` 也做 name↔id 转换。
  - `reviewParams`/`rowToReview`：`department`。
  - `ticketParams`/`rowToTicket`、`commentParams`/`rowToComment`：`department`。
  - `kbParams`/`rowToKb`：`departments` 数组逐个 name↔id。
  - `syncUserAccounts`：写 `review_accounts.department` 时用 `departmentIdOf(u.department)`。
- 新增导出：`interface Department { ord; id; name; createdAt }`、`loadDepartments(): Department[]`。

> 说明：领域对象（`UserAccount.department` / `NodeState.department` / `TicketRecord.department` / `ReviewRecord.department` / `KbArticle.departments` / `TicketComment.department`）**继续暴露部门名**，落地库时才转编号。这样 `platform.ts` 的权限比较、展示、建单逻辑零改动，且部门改名后所有读取自动反映新名。

### 3. `src/platform.ts`（少量）

- 部门下拉来源（L1066 team、L1096 tickets、L1117 kb）与 `normalizeDepartments`（L725）由 `loadUsers().map(u=>u.department)` 改为读取 `loadDepartments().map(d=>d.name)`（含新注册的空部门）。
- 其余部门逻辑（`canExecute`/`canApprove`/`canEditRequirement`/`filterReviewsByUser`/`canAccessTicket`/`filterTicketsByUser`、硬编码 `"程序中台"`/`AI_REVIEW_DEPT`）**不改**（走名称，由 db.ts 转编号）。

### 4. 前端（少量）

- `web/ai-pipeline-app.js` L17-18 硬编码 `DEPARTMENTS`：改为优先取 `window.__PIPELINE__.departments`（平台注入 `loadDepartments()`），缺省回退现有硬编码。`platform.ts` 注入 `__PIPELINE__` 时补 `departments` 字段。
- 其余展示型用法不改。

### 5. `AGENTS.md`（文档同步，必须）

- 顶部平台数据描述：三库 → 五库（users / ai-flows / ai-tickets / ai-kb / ai-chat-reviews）+ 部门表。
- `sqlite.ts` / `db.ts` 模块行：新库文件、schema、departments 表、编号化说明。
- 约束表新增两条：① 部门字段只存编号（`dept-NN`），显示层由 db.ts 解析；② 各库表 SQL 前缀规则（main 无前缀，ai_flows/tickets/kb/chat_reviews 带前缀）。

## 五、Assumptions & Decisions

1. **翻译层放 db.ts**：库内存编号、领域对象暴露名称。这是“只存编号 + 便于改名”的最小改动实现（platform.ts 权限比较零改动）。
2. **messages / token_usage 归 main（users.sqlite）**：账号域附属数据，与用户同库（用户问答未指定，按原推荐布局保留在主库）。
3. **无外键**：跨库无法建外键，departments 关联按逻辑 + get-or-create（与现有 messages/token_usage 约定一致）。
4. **编号格式** `dept-NN`（两位补零，超过 99 自然进位为三位）。
5. **保留自动迁移**：老 `db/ai-flows.sqlite` 作为 `ai_flows` 挂载，从中把 main 域表与 kb 表搬出后再 DROP；`migrated_from_json` 标记（随 settings 在 ai_flows）继续防重复导入。
6. **不改 `.gitignore`**：`db/*.sqlite*` 已覆盖新库文件。
